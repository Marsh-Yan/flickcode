# 长期团队协作 Spec

## 背景

FlickCode 已支持短生命周期的子 Agent、角色配置、任务状态、通知和 worktree 隔离，但这些能力主要服务于一次性的父子任务：

- 没有稳定的小组身份、负责人和成员花名册；
- 子 Agent 之间不能直接通过共享任务和邮箱协作；
- 成员完成一次任务后，无法以原身份恢复上下文继续工作；
- Lead 无法把用户目标拆成共享任务，统一调度成员并集成各成员目录；
- coordinator 模式尚未形成独立的双重开关和工具边界。

本项目新增长期团队协作能力，内部包含三个相互联动的子系统：

1. 持久化小组内核：小组、成员、任务清单、邮箱和并发保护。
2. 成员运行时：隔离终端窗格、进程内轻量后端、成员生命周期和上下文恢复。
3. Lead/coordinator：任务拆解、成员调度、审批、消息、Git 合并和冲突处理。

## 目标

- 让用户可以显式把当前主 Agent 置于某个小组的 Lead 运行上下文。
- 让小组配置、成员身份、邮箱、任务和成员上下文跨运行实例持久化。
- 让成员可以直接协作，不要求所有消息都经过 Lead 中转。
- 让 Lead 可以并行派人成员，跟踪依赖，等待完成并合并代码。
- 让成员在自然停止后进入空闲状态，后续复用同一成员身份恢复工作。
- 让 coordinator 模式通过配置开关和环境变量两把锁显式启用，并收紧发起方工具。
- 保持没有启用团队能力时的普通对话和普通子 Agent 行为不变。

## 功能需求

- **F1：Lead 激活与小组创建**：用户可以通过显式的本地入口创建或打开小组，并把当前主 Agent 绑定为该小组 Lead。未显式激活时，普通主入口不自动获得团队管理能力。
- **F2：长期小组生命周期**：系统可以创建、打开、查询和关闭长期小组。小组拥有稳定身份、名称、Lead、成员花名册和持久化位置；关闭运行实例不会删除小组数据。
- **F3：成员花名册**：小组可以登记、查询和更新成员。每个成员至少包含稳定名称、角色、工作目录、运行后端、审批策略和当前状态。成员身份在运行实例重启或上下文恢复后保持不变。
- **F4：成员运行后端选择**：系统支持隔离终端窗格后端和进程内轻量后端。自动模式根据当前环境和配置优先级选择可用后端，并记录实际选择及原因；首选后端不可用时不得静默降级，若无可用后端则明确拒绝启动成员。
- **F5：共享任务清单**：小组成员可以新增、查询、更新和完成共享任务。任务包含负责人、状态、描述、直接依赖任务和更新时间。直接依赖未完成时，任务不得被标记为可执行；系统拒绝未知依赖和明显的循环依赖。
- **F6：成员协作工具边界**：共享任务和邮箱工具只对 Lead 运行上下文及小组成员运行上下文开放。普通主入口和普通子 Agent 不得看到或调用这些工具；工具执行时仍需校验当前身份和所属小组。
- **F7：点对点与广播消息**：成员可以向指定成员发送消息，也可以向小组广播。消息至少包含发件人、正文、时间戳、已读状态和摘要。落盘时自动补充时间戳，并默认标记为未读。
- **F8：名称注册表与邮箱路由**：发送方先通过小组名称注册表把目标名称解析为成员身份、邮箱位置和运行句柄，再写入目标邮箱文件。独立进程成员收到新消息后还必须触发目标窗格唤醒；不存在的目标必须返回明确错误。
- **F9：邮箱持久化与并发安全**：每个成员拥有独立邮箱文件。写入邮箱前必须取得对应锁文件；拿不到锁时按有界策略重试，超过旧化阈值的锁可以被视为过期并清理。并发写入不得静默覆盖或丢失消息。
- **F10：结构化协作协议**：邮箱支持至少以下结构化消息：任务分配、任务状态更新、审批请求、审批结果、成员空闲通知、任务完成通知和唤醒请求。无法识别的协议消息必须保留并产生可诊断提示，不得被当作批准或任务完成。
- **F11：审批工作流**：需要审批的成员在开始执行前，必须向 Lead 发送包含任务范围、计划、风险和请求标识的结构化审批请求。只有 Lead 针对同一请求标识发送合法批准结构消息后，成员才可以开始执行；驳回、过期或不匹配的回复不得授权执行。
- **F12：Lead 调度流程**：Lead 接收用户目标后，将目标拆解为带直接依赖的共享任务，登记任务负责人，创建或唤醒成员，并跟踪任务状态。Lead 可以直接向成员派发任务、查询进度、终止成员和发送补充指令。
- **F13：成员空闲与上下文恢复**：成员自然完成当前工作后进入空闲状态，并向 Lead 发送通知。Lead 后续向该成员发送新任务时，系统复用原成员身份、工作目录、邮箱和持久化上下文；底层进程是否重新建立不对用户表现为创建新成员。
- **F14：代码集成与冲突处理**：所有成员任务完成后，Lead 可以通过 shell 或受管的 Git 集成入口将各成员工作目录的变更合并回目标分支。可安全判断的冲突由系统或 Lead 处理；无法解决的冲突必须撤销本次集成尝试，并向用户报告冲突文件和原因。
- **F15：coordinator 双重开关**：coordinator 能力只有在配置中的能力开关和用户主动设置的环境变量同时开启时才生效。任一开关关闭时，系统不得进入 coordinator 模式，也不得部分启用其权限变化。
- **F16：coordinator 工具收缩**：coordinator 模式下，发起方不能使用写文件工具，但保留读类工具和 shell。其可用操作限定为派生成员、终止成员、查询和发送协作消息、执行代码合并，以及完成这些操作所需的只读和 shell 能力。模式状态必须对用户和诊断信息可见。

## 非功能需求

- **N1：持久化位置与安全路径**：小组数据存放在用户目录下按小组名隔离的目录中；小组名和成员名必须经过安全规范化，不能通过名称穿越到小组目录之外，也不能覆盖其他小组。
- **N2：原子性与恢复性**：小组元数据和共享任务更新采用临时文件加原子替换或等价机制；邮箱追加在锁内完成。进程崩溃后，已完整写入的数据仍可读取，半写入记录必须被识别并报告。
- **N3：锁的有界等待**：邮箱和共享任务的锁必须有最大重试次数或最大等待时间；过期锁判断要可配置并记录诊断，不允许无限等待。
- **N4：身份与权限隔离**：成员只能访问所属小组和自身授权的工作目录、邮箱和任务；审批失败、身份不匹配或伪造协议消息必须默认拒绝。
- **N5：后端透明度**：后端探测、选择、降级原因、唤醒失败和成员进程异常都必须可查询或写入诊断；任何后端切换不得静默发生。
- **N6：并发与幂等**：多个成员进程可以同时读写共享任务和不同邮箱；重复消费、重复完成通知和重复唤醒不得造成重复执行或状态倒退。
- **N7：资源有界**：成员并发数、邮箱重试、启动等待、唤醒等待和关闭等待均有上限；小组关闭时不得遗留不可诊断的后台运行实例。
- **N8：Git 安全**：Git 操作使用明确的仓库根目录和工作目录，不拼接未经验证的 shell 参数；合并失败时保留成员目录并恢复目标分支到合并前状态。
- **N9：可诊断性**：系统至少能报告小组、成员、任务、消息、后端、审批、唤醒、合并和 coordinator 状态，诊断中不得泄漏凭据或完整敏感消息内容。
- **N10：向后兼容**：未显式进入 Lead 或 coordinator 时，现有普通会话、现有短生命周期子 Agent、已有工具视图和权限行为保持不变。
- **N11：可测试性**：存储、锁、协议校验、依赖检查、后端选择、恢复、工具过滤、coordinator 双锁和 Git 回滚均可通过不依赖真实模型或真实终端的测试验证。

## 不做的事

- 不实现跨机器或跨网络的分布式团队。
- 不实现成员之间的实时流式通信；只实现持久化消息和唤醒通知。
- 不实现复杂的任务依赖表达式、条件分支、动态资源调度或全局规划算法；本阶段只支持直接依赖和基础循环检查。
- 不把团队邮箱或上下文扩展成跨小组、跨项目的长期记忆系统。
- 不改变现有普通子 Agent 的调用协议、角色目录和短任务生命周期语义。
- 不保证终端窗格后端在所有终端程序中可用；不可用时必须明确诊断或选择已声明的替代后端。
- 不允许普通子 Agent 通过配置或伪造调用恢复团队工具。
- 不把成员工作目录的未提交修改直接覆盖到 Lead 工作目录；合并失败不得静默丢弃成员变更。

## 验收标准

- **AC1：Lead 激活与小组创建**：执行显式小组入口后，当前会话成为指定小组 Lead；未激活的普通会话工具列表不包含团队管理和协作工具。
- **AC2：小组持久化**：创建小组并关闭会话，再从磁盘打开同名小组，观察 Lead、成员花名册、任务和持久化位置保持一致。
- **AC3：成员身份恢复**：登记成员后重启团队管理器，观察成员 ID、角色、工作目录、后端和审批策略不变。
- **AC4：后端选择**：在模拟的终端后端可用、不可用和全部不可用环境中启动成员，观察选择结果、原因和失败状态明确；不可用时不发生静默降级。
- **AC5：任务依赖**：创建带直接依赖的任务，观察未知依赖和循环依赖被拒绝，依赖未完成时任务保持阻塞，依赖完成后任务可进入就绪状态。
- **AC6：工具可见性**：比较普通主入口、Lead、普通子 Agent 和团队成员的工具视图，观察只有后两类按身份获得允许的团队工具，伪造调用也被拒绝。
- **AC7：消息字段与路由**：发送点对点消息和广播消息，读取邮箱文件，观察发件人、正文、摘要、自动时间戳和默认未读状态正确，名称解析到正确邮箱。
- **AC8：邮箱并发**：并发写入同一邮箱并模拟旧锁，观察消息不丢失、不互相覆盖，旧锁可被处理，超出重试上限时返回明确错误。
- **AC9：协议校验**：投递任务、状态、审批、空闲、完成和唤醒协议消息，观察各自被正确解析；未知协议保留但不能改变授权或任务终态。
- **AC10：审批闭环**：让需要审批的成员提交计划，观察未收到合法批准前不会执行；批准、驳回、请求 ID 不匹配和过期回复分别产生正确结果。
- **AC11：Lead 并行调度**：输入包含多个独立任务的目标，观察 Lead 可将任务写入共享清单、派发给多个成员并根据消息更新状态。
- **AC12：空闲与恢复**：成员完成任务后观察其进入空闲并通知 Lead；Lead 再发任务后，观察原成员从持久化邮箱和上下文恢复，不创建新的成员记录。
- **AC13：Git 合并与回滚**：让多个成员目录产生变更，观察全部完成后可合并；模拟可处理冲突和不可处理冲突，分别观察合并结果和目标分支回滚报告。
- **AC14：coordinator 双锁**：分别关闭配置开关、缺少环境变量、仅打开其中一把锁和两把都打开，观察只有最后一种情况进入 coordinator 模式。
- **AC15：coordinator 工具收缩**：coordinator 开启后观察写文件和编辑文件工具不可见且不可执行，读类工具、shell、派人、终止、消息和合并能力仍可用。
- **AC16：唤醒与故障诊断**：独立进程成员收到消息时观察目标窗格被唤醒；窗格不存在或唤醒失败时，邮箱消息仍保留且 Lead 收到可诊断失败状态。
- **AC17：兼容性回归**：未进入团队模式时运行普通对话、短生命周期子 Agent、worktree、权限和上下文压缩测试，观察既有行为不变。
- **AC18：端到端团队流程**：用户激活 Lead → 创建小组和成员 → Lead 写入带依赖任务 → 成员并行执行并通过邮箱协作 → 需要审批的成员获批 → 成员空闲通知 → Lead 唤醒并恢复成员 → 完成后 Git 合并或回滚上报，整个流程可观察且无消息丢失。
