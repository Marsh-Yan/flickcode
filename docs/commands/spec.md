# FlickCode 命令注册与分发 Spec

## 背景

FlickCode 当前在 TUI 输入循环中以分支判断处理少量内置命令，例如
`/compact`、`/sessions`、`/resume`、`/plan` 和 `/do`。命令识别、参数解析、AI
请求分流和界面更新分散在交互循环中，新增命令需要继续修改入口分支，容易出现
大小写、别名、帮助信息、补全和交互模式不一致的问题。

用户输入中有一类操作不需要 Agent 推理：清屏、查看状态、切换模式、管理会话等。
另一类操作虽然需要 AI，但提示词和行为已经预设，例如规划、执行计划和代码审查。
这些输入应绕过普通对话入口，由确定性的命令系统处理，从而降低响应延迟和不必要的
Token 消耗。

当前会话已经具备 Agent 模式、计划上下文、上下文压缩、会话归档、记忆、权限和
Token 使用量等能力。本功能负责为这些能力提供统一的斜杠命令入口，不改变它们已有
的核心语义。

## 目标

- 建立启动时完成校验的命令注册中心，统一保存命令元数据和处理入口。
- 在用户提交输入时先识别斜杠命令；命令由本地分发器处理，普通文本才进入 Agent。
- 统一支持命令名大小写不敏感、别名、参数提示、帮助和 Tab 补全。
- 将命令实现依赖的界面操作抽象为稳定的控制接口，使命令不绑定具体渲染框架。
- 为计划模式和执行模式提供可观察的状态标记 `[PLAN]`、`[DEFAULT]`。
- 将现有零散命令迁移到统一机制，同时保留已有 `/plan <task>`、`/do`、会话和
  `/compact` 的用户可见行为。

## 功能需求

### F1：命令注册中心

系统必须提供一个集中注册内置命令的注册中心。每条命令登记以下元数据：

- 规范名称；
- 别名列表；
- 简短描述；
- 用法示例；
- 命令类型：纯本地、影响界面状态、提示词；
- 可选的参数提示；
- 是否隐藏；
- 处理函数。

命令名称和别名在注册时统一按不区分大小写的形式建立索引，但帮助输出保留规范
名称的展示形式。命令名与别名共享同一个命名空间。

启动阶段必须完成全部内置命令注册和冲突校验。规范名称与其他命令的规范名称、
别名或自身别名发生不区分大小写的重复时，启动必须立即以致命错误退出，并报告
冲突名称；不得延迟到用户首次输入时才发现。

### F2：斜杠命令解析

提交输入后，系统必须先进行空输入判断；空输入直接忽略，不调用命令处理函数，也不
调用 Agent。

对非空输入，系统按以下规则解析：

- 去除输入首尾的外层空白后，以 `/` 开头的输入才被视为命令候选；
- 第一个空白字符之前的内容是命令名，之后的全部内容是原始参数；
- 命令名去掉前导 `/` 后转为小写进行查找；
- 参数只去除命令分隔符后的首尾空白，不改写参数内部空格和换行；
- 命令匹配必须支持规范名称和别名；
- `/`、只有空白的命令名、未知命令和命令参数格式错误都不应进入 Agent。

以 `/` 开头但未命中的输入必须输出明确的未知命令提示，并引导用户使用 `/help`。
命令处理失败时只报告该命令的错误并保留交互循环，不因普通输入错误退出程序。

不以 `/` 开头的非空输入必须沿用当前 Agent 对话入口；命令系统不得修改普通文本的
内容或悄悄把普通文本改写成命令。

### F3：三类执行路径

命令分为三类，分发器依据登记类型选择处理路径：

1. **纯本地命令**：只调用本地会话、上下文、配置或状态服务，不向主对话追加用户
   消息，不发起普通 Agent 请求。
2. **影响界面状态命令**：通过界面控制接口改变清屏、模式标记或显示内容，不把
   操作本身当作用户问题发送给 AI。
3. **提示词命令**：由处理函数构造预设的用户意图或提示词，通过统一的“发送用户
   消息”入口交给 Agent；发送过程必须沿用现有会话历史、模式和事件渲染流程。

命令可以在一次处理过程中同时产生界面状态变化和提示词发送，但其注册类型必须
明确其主路由，帮助和诊断信息必须说明该命令是否会触发 AI 请求。预设提示词不得
通过普通文本分支重复发送。

### F4：界面控制抽象

命令实现必须依赖界面控制抽象，而不是直接依赖具体 TUI 或渲染框架。该抽象至少
提供以下能力：

- 显示普通消息、进度消息和错误消息；
- 向当前会话发送一条用户消息并消费 Agent 事件；
- 读取和切换当前交互模式；
- 查询当前会话的 Token 使用量和上下文诊断；
- 刷新状态栏；
- 清理当前界面显示。

抽象实现应允许单元测试使用内存假实现验证命令行为，不需要启动真实终端或连接
Provider。命令系统不能依赖 Rich、prompt_toolkit 等具体渲染 API 才能完成核心分流。

### F5：模式状态和状态栏

会话启动时模式为默认执行模式，状态栏显示 `[DEFAULT]`。计划模式状态栏显示
`[PLAN]`；模式变化后必须立即刷新状态栏。

模式行为如下：

- 无参数 `/plan`：切换到计划模式，不发起 AI 请求；后续普通文本按计划模式提交
  给 Agent。
- `/plan <task>`：保持现有行为，立即以计划模式提交任务给 Agent；规划完成后仍
  保持计划模式，以便继续补充或修改规划。
- `/do`：要求当前存在可执行的计划上下文；满足条件时以执行模式提交预设的
  “执行计划”意图，模式标记切换回 `[DEFAULT]`。不存在计划上下文时只显示错误，
  不改变当前模式，也不发起 AI 请求。
- 计划模式下的普通文本使用计划模式；默认模式下的普通文本使用完整 Agent 模式。

`/do` 的执行行为继续使用已有计划上下文，不要求用户重新粘贴计划。执行失败时，
系统保留会话和计划上下文，以便用户继续处理。

### F6：Tab 补全

输入光标位于斜杠后的命令名区域时，补全器必须基于规范名称和别名进行不区分大小写
的前缀匹配：

- 隐藏命令不得出现在补全候选中；
- 只有一个候选时，按该候选直接补全命令名；
- 有多个候选时，展示候选菜单，不自动选择其中一个；
- 没有候选时不改写用户输入；
- 光标已经进入参数区域后，不继续对命令名做补全。

补全候选与注册中心共享索引，不能维护第二份命令列表。

### F7：帮助和可发现性

`/help` 必须显示所有非隐藏命令的规范名称、别名、简短描述和用法。帮助列表不得
显示隐藏命令。

`/help <command>` 可以显示指定命令的详细用法、参数提示和是否会触发 AI；规范名称
和别名都可查询，查询不区分大小写。未知的帮助对象必须给出错误并继续引导使用
`/help`。

### F8：内置命令

本阶段必须统一注册以下十个高频命令。命令的具体展示文字可以由实现调整，但行为
边界必须符合下表：

| 命令 | 类型 | 行为 |
|---|---|---|
| `/help` | 纯本地 | 展示命令列表或指定命令帮助，不调用 Agent。 |
| `/compact` | 纯本地 | 调用现有上下文压缩入口，展示压缩、摘要、熔断或诊断结果；不把命令文本发送给主对话。 |
| `/clear` | 影响界面状态 | 清理当前界面显示，不删除会话历史、计划上下文或磁盘会话归档。 |
| `/plan` | 提示词 | 无参数时进入计划模式；带任务参数时立即执行现有规划流程。 |
| `/do` | 提示词 | 使用已有计划上下文执行计划，并返回默认执行模式；无计划时显示错误。 |
| `/session` | 纯本地 | 展示当前会话信息和可恢复会话摘要；已有 `/sessions` 行为作为兼容别名或兼容入口保留。 |
| `/memory` | 纯本地 | 展示当前已加载的项目记忆、用户记忆和诊断摘要，不自动修改记忆。 |
| `/permission` | 纯本地 | 展示当前权限模式和已加载规则摘要；本阶段不通过该命令修改命令级权限。 |
| `/status` | 纯本地 | 展示 Provider、模式、计划上下文、上下文估算、Token 使用量和必要的 MCP/诊断状态。 |
| `/review` | 提示词 | 将预设的审查意图发送给 Agent；可选参数作为审查关注点，不执行命令本身。 |

现有 `/exit`、`/quit`、`/resume` 等用户已知入口必须保持向后兼容；它们可以作为
额外的兼容命令注册，不计入上述十个高频命令。`/sessions` 至少作为 `/session` 的
兼容别名保留，已有 `/resume <session-id>` 的参数和恢复语义不得因本功能消失。

### F9：回车入口统一分流

交互式 TUI 的回车提交和非交互管道输入必须共享同一个解析与分发入口，避免两个
输入路径对同一命令产生不同结果。

分流顺序必须是：

1. 空输入直接返回；
2. 斜杠输入交给命令解析器和命令注册中心；
3. 命中命令后按命令类型执行；
4. 斜杠输入未命中时显示未知命令和 `/help` 引导；
5. 只有普通文本才提交给 Agent。

### F10：启动和运行时错误边界

- 别名冲突属于启动配置错误，必须快速失败并明确指出冲突项；
- 未知命令、参数错误和处理失败属于用户输入错误，不得导致程序进程退出；
- 本地命令调用的既有服务错误必须转换为用户可读的错误或诊断消息；
- 提示词命令的发送必须沿用当前 Agent 事件消费、Token 统计、会话持久化和错误
  处理机制；
- 命令处理不能绕过现有权限系统。命令级权限控制不是本阶段需求，但命令触发的
  既有工具执行仍遵循现有权限策略。

## 非功能需求

### N1：确定性和低额外开销

命令解析、查找、帮助过滤和补全候选生成必须只使用本地数据结构，不额外请求 LLM。
命令查找应为常数时间级别的索引访问；命令元数据只维护一份来源。

### N2：可测试性

解析、大小写匹配、别名查找、冲突检测、隐藏命令过滤、补全候选和三类分流必须能在
不启动真实终端、不调用真实 Provider 的条件下测试。每个内置命令的处理结果至少要
能通过内存界面控制假实现观察到。

### N3：向后兼容

普通文本对话、现有 Agent 模式、`/compact`、计划执行、会话列表/恢复、Token 诊断、
权限提示和退出快捷方式的既有可见行为不得因统一注册而回归。兼容命令的大小写和
参数行为也必须保持可用。

### N4：框架解耦

命令核心不直接依赖具体终端渲染框架。更换渲染器或使用管道模式时，命令解析、注册、
分流规则和本地行为应保持一致。

### N5：安全边界

本功能不新增命令级权限绕过，不把未知斜杠输入当作普通用户问题发送给 AI，也不因
`/clear` 删除会话、记忆或项目文件。任何会触发已有 Agent 工具的提示词命令仍受
现有权限和高风险确认流程约束。

## 不做的事情

- 不支持用户自定义命令、配置文件命令或运行时动态注册。
- 不支持由 LLM 动态生成命令定义或动态生成命令元数据。
- 不实现命令级权限控制、命令 ACL、命令白名单或命令级审批策略。
- 不在本阶段重写 Provider、Agent Loop、上下文压缩、会话、记忆或权限模块的核心实现。
- 不把普通斜杠未知输入自动转发给 Agent。
- 不实现复杂的 shell 风格参数解析、引号转义、管道、重定向或子命令语法；命令只
  接收分隔后的原始参数文本。
- 不要求本阶段新增命令插件市场、Skill 发现或第三方命令扩展机制。

## 验收标准

- **AC1：启动冲突快速失败**：注册两个不区分大小写相同的规范名称、别名，或规范
  名称与别名相撞时，启动立即失败并报告冲突名称；无冲突时所有内置命令可被查找。
- **AC2：解析规则正确**：输入 `/STATUS arg text` 能命中 `/status` 并保留参数文本；
  空输入不产生动作；普通文本进入 Agent；未知斜杠输入不进入 Agent 且显示 `/help`
  引导。
- **AC3：帮助完整且隐藏可控**：运行 `/help` 能看到十个内置命令的规范名称、别名、
  描述和用法；隐藏命令不出现在帮助中；`/help STATUS` 能查询到 `/status` 详情。
- **AC4：补全行为正确**：在 `/st` 后 Tab 能补全 `/status`；在多个命令共享前缀时
  显示候选菜单；隐藏命令和参数区域不产生命令候选。
- **AC5：界面抽象可用**：使用内存界面控制假实现执行 `/clear`、`/plan`、`/status`
  时，能观察到清屏、模式切换、状态刷新和消息输出，且测试不需要真实 TUI。
- **AC6：模式状态正确**：启动显示 `[DEFAULT]`；无参数 `/plan` 后显示 `[PLAN]` 且
  不请求 AI；计划模式下普通输入按计划模式处理；`/do` 有计划时执行并回到
  `[DEFAULT]`，无计划时只报错且模式不变。
- **AC7：本地命令不进主对话**：运行 `/help`、`/clear`、`/session`、`/memory`、
  `/permission`、`/status` 和 `/compact` 时，主 Agent 不收到对应的命令文本；
  `/compact` 仍能报告既有压缩服务的实际结果。
- **AC8：提示词命令走统一会话**：运行 `/plan <task>`、`/do`、`/review` 时，预设
  意图通过统一用户消息入口进入当前会话，能继续获得已有流式事件、Token 统计、
  会话记录和权限处理。
- **AC9：兼容行为保持**：现有 `/sessions`、`/resume <session-id>`、`/exit`、`/quit`
  和普通 Agent 对话仍可使用；TUI 输入与管道输入对同一命令产生相同的分流结果。
- **AC10：错误边界正确**：参数错误、未知命令、命令处理异常不会退出交互循环；注册
  冲突会在启动阶段退出；任何错误消息都不泄漏敏感配置或 API Key。

## 方案选择

### 方案 A（推荐）：注册中心 + 统一解析分发器 + 界面控制端口

所有内置命令通过一个注册中心登记，解析器只负责把输入转换为命令名和原始参数，
分发器按命令类型调用处理函数；处理函数依赖抽象的界面控制接口和现有 Session
服务。TUI 和管道模式共同调用分发器，补全器和帮助生成器直接读取注册中心。

优点是命令元数据只有一个来源，冲突能在启动时发现，测试边界清晰，也能逐步迁移
当前 `tui.py` 中的分支而不重写 Agent 和会话模块。代价是需要增加一层命令上下文
和界面适配器，并处理 `/plan`、`/do` 这类同时改变模式和触发 Agent 的命令。

### 方案 B：保留入口分支，抽出共享解析函数

继续在 TUI 中维护各命令的分支，只把命令名解析和参数切分抽成工具函数，再为补全
和帮助额外维护命令表。

优点是初始改动较小。缺点是元数据会在多个位置重复，启动冲突检测难以统一，TUI
与管道模式容易再次分叉，后续添加命令仍需修改入口代码。

### 方案 C：命令对象自带完整 UI 和会话依赖

每个命令对象直接持有 Renderer、PromptSession 和 Session，命令自行完成解析、显示
和 Agent 调用。

优点是单个命令文件容易理解。缺点是强绑定当前渲染框架，难以测试和复用，且会把
命令生命周期、界面状态和会话业务耦合在一起，不适合当前已有 TUI 与管道双入口的
结构。

本阶段选择方案 A，因为它最完整地覆盖注册元数据、启动校验、统一分流、补全和框架
解耦，同时保留现有命令行为的迁移空间。
